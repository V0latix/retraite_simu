# Simulateur de retraite — France

Web app simulating the French pension system at two coupled scales:
- **Macro** — national demography → economy → pension system → yearly balance, under reform scenarios.
- **Micro** (not built yet) — an individual's pension (régime général + AGIRC-ARRCO) computed *inside* a chosen macro context.

The coupling is the point: macro outputs (PASS, point value, indexation, legal age) feed the micro pension calc. Full spec: `docs/cahier-des-charges.md`.

## Stack
React 19 + Vite + TypeScript (strict) + Tailwind v4. Charts: Recharts. Tests: Vitest. Engine runs in a Web Worker. Static hosting on Vercel. No backend.

## Architecture invariants (do not break)
- **Engine is 100% React-free** (`src/engine/`). Pure, deterministic, testable in isolation.
- **Single projection entry point:** `project(state0, hypothesisSet, horizon) => TimeSeries` (`src/engine/project.ts`). Same signature in deterministic and (future) stochastic mode.
- **A scenario is data, not branches.** Reform levers live in `HypothesisSet.policy` as functions of time — never an `if` in the engine.
- **All scale/barème numbers live in data**, never hard-coded in engine logic. Currently `src/data/seed.ts` (parametric placeholder). Phase 0 replaces it with strict versioned INSEE/HMD/COR JSON.

## Observed vs projected (invariant)
Every time-series chart shows **observed data solid, projected data dashed**, with a `frontier()` rule at the boundary. The convention lives in `src/ui/observed.ts` (`mergeObservedProjected`, `frontier`, `PROJECTED_DASH`) + `ObservedProjected.tsx` (legend) — reuse it, never re-improvise per chart. The engine stays untouched: history is display data, loaded from `historical.json` / `historicalPyramid.json` and merged in the UI. The join year appears in both the observed and projected fields so the segments meet (this is also what COR's own workbooks do). Micro/career charts split at `BASE_YEAR` but are labelled *carrière passée / projetée*, never "observé" — the salary is user input even for past years.

## Data status
- **Observed series** (`node scripts/ingest-historical.mjs`): COR rapport annuel juin 2025 workbooks → dépenses/ressources/solde % PIB, cotisants, retraités, PIB (2002-2024, `Obs` rows); ratio 20-64/65+ (1962-2024); réserves du système au 31/12/2024 = 213,8 Md€ ≈ 7,3 % PIB (Tab 2.3), used to anchor the cumulative-balance chart. INSEE POP3 → pyramides observées 1946 (ordonnances créant le régime général) → 2025; champ *France métropolitaine* before 1991, *France* after — stored per year, never spliced. Retirees lag a year behind (holes are `null`).
- **Demography = real INSEE** (Projections 2021-2070): qx/fertility/migration by age 2025-2070, initial 2025 pyramid. The 7 INSEE variant JSONs are still ingested and on disk, but only `central.json` is loaded — the variants are now slider positions (see below). Regenerate via `node scripts/ingest-insee.mjs`. Calibration: our cohort-component reproduces INSEE's 2070 total (~69M vs 68.1M, ~1.3%) and 65+ share (~30%).
- **Extrapolation past 2070** (`BeyondDataPolicy` = hold/trend/converge, §7) stays in the engine (`atYear`, loader.ts) but is no longer a UI choice: every caller takes the `'hold'` default.
- **Hypotheses are sliders, a scenario is a set of slider positions.** `PolicyParams` carries `tfr` / `netMigration` alongside `productivity` / `unemployment`; `applyHypotheses` (`src/data/hypotheses.ts`) rescales the scenario's yearly totals onto them, age/sex profiles preserved, no engine change. `SCENARIO_PRESETS` (`src/data/scenarioPresets.ts`) is the only place a scenario is defined — same pattern as `REFORM_PRESETS`. Three remain: **central** (INSEE/COR), **pragmatique** (observed trends: TFR 1,45, migration +176k, chômage 7,4 %, + risk overlay), **choc-recession** (the only one still differing by *data*, an unemployment shock shape). The old fécondité/EV/migration/COR-productivité variants are slider values now.
- **A law is a calendar keyed by GÉNÉRATION, a proposal is a flat delta.** `PolicyParams.schedule` (`PolicyAnchor[]`, serializable — it crosses postMessage) carries anchors keyed by **année de naissance**, which is how pension law is actually written (2023: 62 → 64 ans, +3 mois par génération, gén. sept. 1961 → 1968). `buildHypotheses` turns them into `cohortPolicy(generation)`; missing générations interpolate, outside the range clamps (`interpByYear` in `loader.ts`, shared with the COR points — `atSchedule` just remaps the key). `policy(year)` keeps only the flat levers. In `project()` the per-year scalar legal age became `effAge[a]` = âge de sortie de la génération `year - a`, so **the calendar is sticky**: whoever liquidated at 62 ans 9 mois stays retired when the age rises, and a lever no longer moves the whole 62-64 stock. That fix alone brought the LFSS-2026 suspension from ≈7 Md€ down to ≈2 Md€ in 2027, against the government's 1,8 Md€. No schedule ⇒ every génération gets the same flat age ⇒ **byte-identical** output (verified over 2025-2070 × 3 scenarios).
- **The 2023 calendar lives in `DEFAULT_POLICY`** (`systemParams.json` `policy.schedule`), not just in the reform template: `buildCorCalibration()` is built on it, so the reference still tracks COR EEC at every horizon while stopping the old nonsense of applying 64 ans in 2025 to générations still at 62-63. Reform templates are deviations *from* that calendar. A flat `legalAge`/`requiredQuarters` passed without a schedule **drops** the inherited one — in `buildHypotheses` (engine callers) and in `setP` (App.tsx) — else the calendar would silently swallow the slider. Other sliders leave it alone.
- **Legal age is fractional and damped.** `retiredWeight()` (`project.ts`) pro-rates the boundary cohort so 62,75 = « 62 ans 9 mois » works; at an integer age it is exactly the old 0/1 step, so the COR calibration is untouched. `legalAgeEffectiveness` (0,29, `systemParams.calibration`, anchored on `legalAgeRef` = 64 so the reference is unshifted) damps the lever: raw, it priced the 2023 reform at ≈59 Md€ at 2030 against a published 10 (Cour des comptes) – 17,7 (étude d'impact) Md€ range. Raised from 0,26 when the per-génération resolution shrank the same gap mechanically. Guarded by `validation.test.ts` (2040 is the binding year, ≈10,9 Md€). Known limit: one linear elasticity can't be right for both a marginal 2-year move and a return to 60.
- **Pension amounts (macro).** `YearResult.avgPension` = pension brute moyenne, euros constants annuels, *before* the COR benefit multiplier (which drives the mass, not the individual amount) but *after* `pensionCap`. Observed counterpart in `historical.pensions` (COR onglet `Rému_pensions`: pension brute moyenne de l'ensemble des retraités 2005-2023, rémunération brute moyenne des cotisants 2002-2024, € 2023/mois). Charted together in the *système* group, both legs rebased with the existing `rebaseFactor` — the model's per-head levels aren't COR's administrative ones. **`pensionCap`** (€/mois) écrête via `pensionDistribution.json`, deciles expressed as ratios to the mean (Σ = 10) scaled by `avgPensionObservedMonthly` (1 770 €, COR 2023) and drifted with the model's own pension dynamics — ratios, so the COR calibration is untouched. Known ceiling, flagged in code: each decile is treated as concentrated on its mean, so a cap set *inside* the top decile is an order of magnitude, not a costing.
- **`ingest-historical.mjs` merges, never overwrites.** `historical.json` also holds hand-curated blocks the script can't produce (fécondité/migration/chômage observés, inflation INSEE, réserves FRR). It used to clobber them.
- **Precedence rule (do not break):** in the macro view the sliders *are* the scenario, so `runMacro` uses the user's policy. In multi-scenario views (`runCompare`, `runMicro`) one shared policy would flatten every scenario onto the same hypotheses, so the scenario's own preset **overrides** it (`scenarioPolicy()` in the worker); reform levers still come from the user.
- **No life-expectancy slider**: dropping `mortality-low/high` removed the model's strongest sensitivity with no replacement. The JSONs are still on disk — an EV slider means interpolating qx between the three matrices.
- **Finance block calibrated to COR** (Phase 4): constant (real) euros, base-year anchored to the COR June 2025 reference (`corReference.json`), **convention EEC** (« effort de l'État constant » — the economically-meaningful solde used by the Cour des comptes/public debate, which neutralises State balancing transfers) — dépenses ≈13.9% PIB, solde ≈−0.48% PIB (≈−8.7 Md€) in 2025; solde reaches ≈−1.4% PIB in 2070. The COR headline convention EPR (fonction publique équilibrée par construction) would show ≈0 today but converges to the same −1.4% in 2070; EPR≈EEC for observed years, they diverge only in projection. Outputs in % PIB. `systemParams.json` `calibration` block holds the base anchors + `pensionDriftShare` (noria). **Central tracks COR EEC at every horizon** (`corReference.json` points 2025/30/40/50/60/70): `loader.ts` `buildCorCalibration()` runs the central scenario once with the raw taper, then derives a per-year benefit multiplier `depMul` (flattens dépenses to COR's ~14%, killing the old mid-century overshoot to ~15.7%) and an `otherResPct` (pins resources to COR), passed to `project()` via `EconInit.calibration`. The raw single-year taper remains the fallback when no calibration is supplied (`DEFAULT_ECON`, engine tests). Every scenario and reform lever reuses the *same* calibration, so they deviate from COR through their own demography/contributions — sensitivity is preserved (e.g. 2070 solde: central −1.4%, pragmatique −3.1%, TFR 1,2 → −4.7%; +5 pt cotisation → +1.4 pt). The model→COR gap is shown in the Validation view.
- **Micro engine (Phase 3) runs in constant (real) euros.** RG (SAM = 25 best capped at PASS, décote/surcote, proratisation) + AGIRC-ARRCO points. Barèmes in `pensionParams.json` — hand-curated/approximate, flagged. The macro→micro coupling (§5.4) ties the AGIRC-ARRCO point value to each scenario's `dependencySystem` (`couplingSensitivity` k, gentle) so the same career yields a different pension per scenario. Replacement rates land in the realistic range (SMIC ~64%, médian ~53%, cadre ~34%); the per-scenario spread is small for near-2049 retirees (honest) and widens for younger cohorts. HMD skipped: INSEE's 1962-2070 qx covers Phase-5.

## Stochastic mode (Phase 5)
Lee-Carter fitted at build time on INSEE observed qx 1962-2021 (`scripts/ingest-insee.mjs` → `leeCarter.json`: α/β/κ, drift, σ per sex). The generator (`src/engine/scenarios/stochastic.ts`) perturbs the **calibrated central** — qx·exp(β_a·z_t) with z a driftless RW (σ from the fit), plus RW factors on fertility/migration (hand-tuned σ, flagged) — so the median tracks the deterministic central and the fan is data-grounded. `runStochastic` (fanchart.ts) runs `project()` K times → p5/25/50/75/95 bands. `project()` itself is unchanged (invariant held). Fan tab covers solde %PIB, dependency, 65+ share.

## Macro view UX (shared patterns)
Sidebar = sticky (`lg:sticky lg:self-start`, needs `self-start` or the grid item stretches), four cards: **Scénario** (preset picker + horizon) → **Hypothèses** (fécondité, migration, productivité, chômage) → **Leviers de réforme** → **Contexte & risques** (Pragmatique only). Picking a scenario moves the Hypothèses sliders in front of the user; deviating from them shows « — modifié » on the picker and the `Réinitialiser · N modifiés` button (no `custom` scenario id). Per-lever pedagogy lives in `<Hint>` (native `<details>`, `Levers.tsx`) — never inline paragraphs between sliders. The main column opens on `KpiStrip` (solde/dépenses/dépendance à l'horizon + « impact de vos leviers » = the same scenario re-run with its own preset as baseline, one extra worker). Charts are grouped in three `<Group>`s (système / hypothèses / contexte); chart chrome (`GRID`, `AXIS`, `TOOLTIP`) and legends (`<Legend><Swatch/></Legend>`) are shared — don't re-inline `CartesianGrid`/`stroke`/`<svg><line/>` per chart.
